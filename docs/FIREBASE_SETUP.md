# Firebase: usuarios, permisos y puesta en marcha

## Modelo de usuarios

Cada persona tiene una cuenta real en Firebase Authentication. Su documento de perfil está en `usuarios/{uid}`, donde `{uid}` es el identificador generado por Authentication. El correo es un campo, nunca el ID del documento. Los roles admitidos son `admin` y `editor`. Solo `admin` puede abrir el módulo Usuarios y llamar a sus rutas de creación o edición. El editor puede entrar al módulo de contenidos.

El formulario de `/admin` crea la cuenta en Authentication desde una ruta de servidor con Firebase Admin SDK y después crea `usuarios/{uid}`. Si falla Firestore, se elimina la cuenta recién creada para evitar una cuenta huérfana. El alta acepta la cédula de diez dígitos y conserva solamente sus últimos cuatro en Firestore. Genera una clave aleatoria que no se muestra ni se almacena. Se envía al correo un enlace de activación de Firebase; al abrirlo en `/admin`, la persona confirma el correo y debe establecer su contraseña antes de usar el panel. El servidor guarda la clave nueva, retira el bloqueo de primer ingreso, revoca las sesiones previas y pide entrar de nuevo. En accesos posteriores entra con correo y contraseña. Al editar, el nombre se actualiza en Authentication y Firestore; el rol se actualiza en Firestore y se revocan los tokens de actualización cuando cambia.

La cédula no se usa como contraseña en esta implementación provisional. Es un identificador personal de baja entropía, por lo que convertirlo en clave permitiría ataques con datos conocidos. El acceso por nombre completo tampoco está implementado porque los nombres pueden repetirse. Estas dos decisiones deben resolverse antes de llamar definitivo al flujo de acceso.

## Configuración necesaria

1. En Firebase Authentication, habilitar **Correo electrónico/contraseña** y **Enlace por correo electrónico**; registrar los dominios autorizados, incluido el dominio final de Vercel. El enlace de activación necesita ambos métodos.
2. En Authentication > Configuración, deshabilitar las acciones de **creación y eliminación de cuentas por usuarios finales**. Firebase seguirá permitiendo crear cuentas desde Admin SDK, pero bloqueará altas directas desde el SDK web.
3. Configurar y probar las plantillas de enlace de acceso y recuperación de contraseña. Definir una política de contraseña fuerte. La activación por enlace verifica la titularidad del correo; después se exige una contraseña nueva de 12 caracteres como mínimo.
4. En Firebase Console → Configuración del proyecto → Cuentas de servicio → Firebase Admin SDK, generar una clave privada. La configuración local activa está unificada en `.env`, que Git ignora. `FIREBASE_SERVICE_ACCOUNT_JSON` contiene el JSON de la cuenta de servicio como una sola línea. Nunca poner la clave en `NEXT_PUBLIC_*` ni en Git. Reiniciar el servidor después de cambiar `.env`. En producción, configurar la misma variable como secreto del servidor en el proveedor de despliegue.
5. El administrador existente tiene un documento antiguo `usuarios/{correo}`. Tras verificar el token, el correo y el rol del documento antiguo, el servidor crea `usuarios/{uid}` en el primer acceso. Comprobar que aparece en Usuarios y que puede entrar de nuevo después de cerrar sesión. El documento antiguo no concede permisos con las reglas nuevas; revisarlo y eliminarlo manualmente después de comprobar la migración. `FIREBASE_BOOTSTRAP_ADMIN_UID` queda como mecanismo excepcional para una cuenta verificada sin perfil antiguo; no establecerlo salvo verificación explícita del UID.
6. Publicar [firestore.rules](../firestore.rules) y [storage.rules](../storage.rules) desde Firebase CLI o la consola. `firebase.json` está configurado para ambas. Con la CLI instalada e iniciada en la cuenta correcta: `firebase deploy --project maresa-project --only firestore:rules,storage`. Revisar primero que `maresa-project` sea el proyecto que sirve al sitio. Las reglas de Storage consultan Firestore; Firebase puede solicitar habilitar el permiso de acceso entre productos la primera vez.
7. Desplegar la nueva aplicación y probar en una cuenta administradora verificada: crear Editor con cédula y correo reales de prueba, comprobar que aparecen Authentication y `usuarios/{uid}`, abrir el enlace en otro navegador, establecer la clave, cerrar sesión, volver a entrar, recargar `/admin`, cambiar el rol y verificar que la API de usuarios se deniega al Editor. Probar también un enlace caducado y un usuario no verificado.

## Límites operativos

- Las reglas de Firestore y Storage protegen las peticiones directas de los SDK web. El Admin SDK omite esas reglas, por eso cada ruta del servidor comprueba token, revocación, cuenta habilitada y rol antes de escribir.
- El módulo Contenidos guarda cada sección en `site_content/{section}` y sube las imágenes a `site-images/`. El módulo Catálogo guarda sus filas en `catalog/{id}`. Las altas e importaciones quedan como borrador; el administrador debe revisar una ficha y marcarla como publicada. El buscador público consulta solo documentos con `published == true`, y las reglas impiden leer borradores desde una sesión pública. Estas operaciones requieren publicar las reglas y configurar Firestore y Storage. Las tarjetas educativas de tecnologías no representan productos a la venta.
- Las reglas de Firestore permiten crear solicitudes B2B públicas con validación de tamaño y campos. Para frenar abuso automatizado se necesita además App Check y/o una ruta de servidor con límite de frecuencia.
- No se modificó el proyecto Firebase ni Vercel desde este repositorio. Las reglas y variables requieren configuración y despliegue en los servicios reales.
